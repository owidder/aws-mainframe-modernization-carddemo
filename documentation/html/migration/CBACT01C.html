CBACT01C — Migration TODOs

Batch Account Spring Boot · Spring Batch · JPA/Hibernate · PostgreSQL
Source: app/cbl/CBACT01C.cbl
CBACT01C reads every record from the master credit card account file (VSAM KSDS, sequential access) and distributes each account into three output files in parallel.
I/O Files
DDNameFormatContentRole
ACCTFILE VSAM KSDS, sequential read Input — master account file, 300 bytes/record input
OUTFILE Sequential flat Full account details (11 fields, reformatted reissue date) output
ARRYFILE Sequential structured Account ID + 3 hardcoded balance/debit scenarios per account output
VBRCFILE Variable-length (12 or 39 bytes) Two record types: short (ID + status) and long (ID + bal + limit + year) output
Architecture decisions
Resolve before writing any code
AD-1 Account input source

ACCTFILE is a VSAM KSDS on the mainframe. For the Java batch job, decide:

  • Option A — DB (recommended) — Accounts are already in PostgreSQL (populated by another migration step). Use JpaCursorItemReader.
  • Option B — File — Export VSAM to a fixed-length flat file (300 bytes/record). Use FlatFileItemReader with a custom FixedLengthTokenizer.
Recommendation: Option A if the Account entity exists in the target DB, otherwise Option B.
AD-2 Output file format

The three output files are flat binary/fixed-length. For Java:

  • Keep as flat files (FlatFileItemWriter) — drop-in replacement for downstream consumers
  • Write to PostgreSQL tables — cleaner for modern downstream systems
Document the choice; it affects all three ItemWriter implementations.
AD-3 ARRYFILE purpose

The array file always writes hardcoded scenario values (1005.00, 1525.00, -1025.00, -2500.00). This looks like test data generation, not production logic.

Clarify with business: is this file still needed in Java, or was it a mainframe test artefact? (See also BR-4)
AD-4 VBRCFILE consumers

The variable-length record file (2 record types per account) is unusual. Identify the downstream system(s) that read it.

If the consumer is also being migrated, the interface can be redesigned (e.g., two separate files or a DB view).
AD-5 COBDATFT replacement

The assembler date-conversion utility is called once per account. Replace with Java DateTimeFormatter — no external call needed. See DEV-6.

DM-2 AccountFlatRecord output DTO (for OUTFILE)

Maps OUT-ACCT-REC (11 fields). Note: OUT-ACCT-CURR-CYC-DEBIT defaults to 2525.00 when source value is zero (business rule BR-2).

DM-3 AccountArrayRecord output DTO (for ARRYFILE)

Maps ARR-ARRAY-REC: account ID + 3 occurrences of (currentBalance, cycleDebit). Only 3 of the 5 array slots are populated — see business rule BR-4.

  • Long (39 bytes): VB2-ACCT-ID (11) + VB2-ACCT-CURR-BAL (12) + VB2-ACCT-CREDIT-LIMIT (12) + VB2-ACCT-REISSUE-YYYY (4)
DM-5 COMP-3 (packed decimal) handling

OUT-ACCT-CURR-CYC-DEBIT and ARR-ACCT-CURR-CYC-DEBIT use USAGE IS COMP-3.

  • If reading/writing raw binary files: use BigDecimal with explicit packed-decimal encoding/decoding (e.g. Apache Commons PackedDecimal or a custom codec)
  • If using DB or text format: BigDecimal with standard scale suffices

Spring Batch job
DEV-1 AccountExportJobConfig — Job and Step 
@Bean
public Job accountExportJob(Step accountExportStep) {
    return jobBuilderFactory.get("accountExportJob")
        .start(accountExportStep)
        .build();
}

@Bean
public Step accountExportStep(ItemReader<Account> reader,
                               ItemProcessor<Account, AccountExportResult> processor,
                               ItemWriter<AccountExportResult> compositeWriter) {
    return stepBuilderFactory.get("accountExportStep")
        .<Account, AccountExportResult>chunk(100)
        .reader(reader)
        .processor(processor)
        .writer(compositeWriter)
        .faultTolerant()
        .noSkip(Exception.class)   // any error = job failure, matching ABEND behaviour
        .build();
}
COBOL abends on any I/O error — set noSkip / noRetry to replicate strict fail-fast semantics. Do NOT use skip policies unless the business explicitly allows partial output.
DEV-2 AccountItemReader
  • DB path: JpaCursorItemReader with SELECT a FROM Account a ORDER BY a.accountId
  • File path: FlatFileItemReader with FixedLengthTokenizer, field widths from CVACT01Y (total 300 bytes). Map COMP-3 fields via custom FieldSetMapper.
DEV-3 AccountExportProcessor — core business logic

Input: Account. Output: AccountExportResult (holds all output records). Steps per account:

  1. Log all fields to SLF4J INFO (replaces 1100-DISPLAY-ACCT-RECORD DISPLAY statements)
  2. Populate flat record (replaces 1300-POPUL-ACCT-RECORD) — see DEV-6 for date conversion
  3. Apply default debit rule (replaces IF ACCT-CURR-CYC-DEBIT = ZERO MOVE 2525.00)
  4. Populate array record (replaces 1400-POPUL-ARRAY-RECORD) — see BR-4
  5. Populate short + long VBR records (replaces 1500-POPUL-VBRC-RECORD)
DEV-4 CompositeItemWriter 
@Bean
public CompositeItemWriter<AccountExportResult> compositeWriter(...) {
    return new CompositeItemWriterBuilder<AccountExportResult>()
        .delegates(flatFileWriter, arrayFileWriter, vbrFileWriter)
        .build();
}
DEV-5 Three ItemWriter implementations
  • AccountFlatFileWriter — writes AccountFlatRecord to OUTFILE. Use FlatFileItemWriter with FormattedLineAggregator. Field widths must match OUT-ACCT-REC layout exactly if binary-compatible output is required.
  • AccountArrayFileWriter — writes AccountArrayRecord to ARRYFILE. Each record: account ID (11) + 3 × (balance 12 + debit 12) + filler 4 = 75 bytes. Only implement if AD-3 confirms this file is still needed.
  • AccountVbrFileWriter — writes two records per account to VBRCFILE. Must prepend a 4-byte RDW (Record Descriptor Word) per record if the downstream consumer expects standard mainframe variable-length format. Short: 12 + 4 = 16 bytes on disk. Long: 39 + 4 = 43 bytes on disk.
DEV-6 DateConversionService — replace COBDATFT

The assembler call CALL 'COBDATFT' USING CODATECN-REC (app/cbl/CBACT01C.cbl:231) converts the reissue date. Input type 2 = YYYY-MM-DD, output type 2 = YYYYMMDD (no separators).

@Service
public class DateConversionService {
    private static final DateTimeFormatter IN  = DateTimeFormatter.ofPattern("yyyy-MM-dd");
    private static final DateTimeFormatter OUT = DateTimeFormatter.ofPattern("yyyyMMdd");

    public String reformatReissueDate(String yyyyMmDd) {
        if (yyyyMmDd == null || yyyyMmDd.isBlank()) return "        ";
        return LocalDate.parse(yyyyMmDd.strip(), IN).format(OUT);
    }
}
Handle blank/null input gracefully — mainframe FILLER fields may produce spaces.

Error handling
EH-1 Replace ABEND pattern

COBOL calls 9999-ABEND-PROGRAM on any I/O failure, which calls CEE3ABD with abend code 999.

app/cbl/CBACT01C.cbl:406–411
  • Throw an unchecked AccountExportException (or RuntimeException) from any writer
  • Configure the Step with .noSkip(Exception.class) → job stops immediately with FAILED exit status
  • The CEE3ABD call has no Java equivalent — JVM exit code and Spring Batch job status are sufficient for operators
EH-2 File open/close errors

COBOL explicitly checks open/close status for all four files.

app/cbl/CBACT01C.cbl:317–404 — Paragraphs 0000-ACCTFILE-OPEN through 4000-VBRFILE-OPEN and 9000-ACCTFILE-CLOSE
  • In Spring Batch, resource open/close is handled by the framework
  • Verify input file exists / DB is reachable before starting the step
  • Wrap output resource creation in try-with-resources or Spring resource lifecycle
EH-3 I/O status display → structured exception log

9910-DISPLAY-IO-STATUS decodes the 2-byte COBOL file status into a readable 4-digit code.

app/cbl/CBACT01C.cbl:413–426 
log.error("I/O failure on {}: {} — {}",
