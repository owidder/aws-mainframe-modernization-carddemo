COBIL00C.CBL

Enables cardholders to pay their credit card account balance in full through an online bill payment transaction.

The program presents a bill payment screen where a customer service representative or cardholder enters an account ID to retrieve the current outstanding balance. The user must explicitly confirm the payment (Y/N) before the transaction is processed. Upon confirmation, the program creates a full-balance payment transaction record in the transaction file, then updates the account balance to zero by subtracting the paid amount. The payment is recorded as a 'BILL PAYMENT - ONLINE' transaction with type code '02', category code '2', and a system-generated unique transaction ID with timestamps.

Business Rules
  • Account ID must not be empty; the payment cannot proceed without a valid account identifier.
  • The customer must explicitly confirm the payment by entering 'Y' before any funds are applied; entering 'N' cancels and clears the screen.
  • Only valid confirmation values are accepted (Y/y or N/n); any other value triggers an error message.
  • A bill payment can only be processed if the account has a positive outstanding balance; accounts with zero or negative balance are rejected with the message 'You have nothing to pay'.
  • The payment always covers the full current account balance — partial payments are not supported by this program.
  • After a confirmed payment, the account balance is reduced to zero by computing: new balance = current balance minus payment amount.
  • Each bill payment generates a new unique transaction ID by reading the last transaction ID and incrementing it by 1.
  • The payment transaction is timestamped with both origination and processing timestamps set to the same current system time.
  • Navigation: PF3 returns the user to the previous screen (defaulting to the main menu COMEN01C), and PF4 clears the current screen.

Paragraph Overview

MAIN-PARA

MAIN-PARA is the central orchestration paragraph that controls the entire bill payment session flow. It determines whether to initialize a new session, process user input, or handle navigation actions, then returns control to the CICS transaction manager to await the next user interaction.

Lines 99–153

PROCESS-ENTER-KEY

This paragraph orchestrates the full bill payment workflow when the user submits the payment screen: it validates the account ID and confirmation input, retrieves the current balance, and — upon explicit customer confirmation — creates a payment transaction record and zeroes out the account balance.

Lines 154–248

GET-CURRENT-TIMESTAMP

Captures the exact current system date and time to serve as the official timestamp for the bill payment transaction. This timestamp is recorded on the payment record to document precisely when the transaction was originated and processed.

Lines 249–272

RETURN-TO-PREV-SCREEN

Handles the user's request to exit the bill payment screen and return to the previous application screen. It ensures a safe handoff back to the calling screen (defaulting to the sign-on screen if no prior navigation context exists), passing along the identity of the current program before transferring control.

Lines 273–288

SEND-BILLPAY-SCREEN

Prepares and displays the bill payment screen to the user, including any status or error messages, so the cardholder or representative can view the current payment details and take action. This is the final step in rendering the payment interface after all data has been assembled.

Lines 289–305

RECEIVE-BILLPAY-SCREEN

Captures the data entered by the user on the bill payment screen, collecting the account ID and payment confirmation choice submitted by the customer service representative or cardholder. This is the entry point for processing any user input before validation and payment execution begin.

Lines 306–318

POPULATE-HEADER-INFO

Populates the standard screen header area with current date, time, application titles, transaction name, and program identity before displaying the bill payment screen to the user. This ensures every screen presented to the customer service representative carries consistent, accurate contextual information for audit and navigation purposes.

Lines 319–342

READ-ACCTDAT-FILE

Retrieves the credit card account record from the account master file using the provided account ID, locking it for update to ensure data integrity during payment processing. Handles cases where the account is not found or a system error occurs by halting the payment and notifying the user.

Lines 343–376

UPDATE-ACCTDAT-FILE

Persists the updated account record — with the balance reduced to zero — back to the account master file after a confirmed bill payment. Handles any file update failures by alerting the user and halting further payment processing.

Lines 377–407

READ-CXACAIX-FILE

Looks up the card number associated with the account being paid by searching the cross-reference index using the entered account ID. Handles cases where the account is not found or the lookup fails, preventing the payment from proceeding without a valid linked card.

Lines 408–440

STARTBR-TRANSACT-FILE

This paragraph initiates a browse (sequential read) of the transaction history file, starting from a specific transaction ID position, in order to locate the most recently recorded transaction. This is a prerequisite step to determining the last-used transaction ID so that a new unique ID can be generated for the incoming bill payment.

Lines 441–471

READPREV-TRANSACT-FILE

This paragraph retrieves the most recent transaction record from the transaction history file in reverse order, in order to determine the last used transaction ID so that a new unique ID can be generated for the incoming bill payment. It handles both successful retrieval and edge cases such as an empty file or system errors.

Lines 472–500

ENDBR-TRANSACT-FILE

Closes the sequential browse operation on the transaction history file after the last transaction ID has been read and incremented. This step is required to release the file cursor before a new payment transaction record can be written.

Lines 501–509

WRITE-TRANSACT-FILE

This paragraph physically records the confirmed bill payment transaction into the transaction history file, then informs the user of the outcome — displaying a success confirmation with the unique transaction reference, or an appropriate error message if the write operation fails.

Lines 510–551

CLEAR-CURRENT-SCREEN

Resets the bill payment screen to a clean state by clearing all entered data and redisplaying a blank payment form. This allows a customer service representative or cardholder to start a new payment entry without residual data from a previous session.

Lines 552–559

INITIALIZE-ALL-FIELDS

Resets the bill payment screen to a clean, empty state by clearing all user-facing input fields and any informational messages. This ensures no residual data from a previous transaction is visible or carried forward when the screen is refreshed or reused.
