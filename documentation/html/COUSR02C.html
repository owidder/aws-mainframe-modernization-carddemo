COUSR02C.CBL

Allow administrators to look up and update an existing user account's details in the CardDemo system's user security file.

The program presents an administrator with a user update screen where they can enter a User ID to retrieve an existing user's profile (first name, last name, password, and user type) from the security file. Once the user record is displayed, the administrator can modify any of the editable fields and save the changes by pressing PF5, or navigate away using PF3/PF12 which also triggers a save attempt before returning to the previous screen. The program validates that all mandatory fields (User ID, First Name, Last Name, Password, User Type) are non-empty before writing changes, and only performs the file update if at least one field has actually been modified.

Business Rules
  • User ID is mandatory and cannot be empty when looking up or updating a user account
  • First Name, Last Name, Password, and User Type are all mandatory fields and cannot be left blank when saving an update
  • A file update is only performed if at least one field (First Name, Last Name, Password, or User Type) has been changed from its current stored value — no unnecessary writes occur
  • If the entered User ID does not exist in the security file, the update is rejected with a 'User ID NOT found' error message
  • The record is read with an UPDATE lock (CICS READ UPDATE) to prevent concurrent modification of the same user record
  • PF3 saves any pending changes and returns the administrator to the calling program (defaulting to the Admin menu COADM01C if no calling program is recorded)
  • PF12 discards any unsaved changes and navigates directly back to the Admin menu (COADM01C) without saving
  • PF5 explicitly saves the updated user information while keeping the administrator on the update screen
  • PF4 clears the current screen input without saving
  • If the session communication area is empty (no prior context), the user is redirected to the sign-on screen (COSGN00C), preventing unauthorised direct access

Paragraph Overview

MAIN-PARA

MAIN-PARA is the central orchestration paragraph that controls the entire user update session flow. It determines whether an administrator is starting a new session or continuing an existing one, then routes their key presses to the appropriate business actions such as saving changes, clearing the screen, or navigating away.

Lines 82–142

PROCESS-ENTER-KEY

This paragraph handles the administrator's request to look up a user account by User ID. It validates that a User ID has been entered, retrieves the matching user profile from the security file, and displays the editable account details on screen for the administrator to review and modify.

Lines 143–176

UPDATE-USER-INFO

This paragraph validates all mandatory fields on the user update screen, then compares the administrator's submitted changes against the current stored profile to determine whether any fields were actually modified before committing the update to the security file. It enforces data integrity by rejecting blank fields and avoiding unnecessary file writes when nothing has changed.

Lines 177–249

RETURN-TO-PREV-SCREEN

This paragraph handles the navigation away from the user update screen, returning the administrator to the appropriate previous screen. It ensures the session context is correctly stamped with the originating transaction before handing control to the destination screen.

Lines 250–265

SEND-USRUPD-SCREEN

Prepares and displays the User Update screen to the administrator, showing current user account details along with any validation or status messages resulting from the most recent action.

Lines 266–282

RECEIVE-USRUPD-SCREEN

Captures the administrator's input from the user update screen, reading all field values the administrator has entered or modified (such as first name, last name, password, and user type) so the program can proceed with validation and saving changes to the user account.

Lines 283–295

POPULATE-HEADER-INFO

Populates the standard header section of the User Update screen with current date, time, application titles, and transaction identifiers, ensuring the administrator always sees accurate context information at the top of the screen before any user data is displayed or edited.

Lines 296–319

READ-USER-SEC-FILE

This paragraph retrieves an existing user's account record from the security file with an exclusive update lock, preventing other processes from modifying the same record simultaneously. Based on the outcome, it either displays the user's current details ready for editing, or presents the administrator with an appropriate error message if the user cannot be found or the file is unavailable.

Lines 320–357

UPDATE-USER-SEC-FILE

This paragraph commits the administrator's changes to the user security file by permanently writing the updated user profile record. It then informs the administrator of the outcome — success, user not found, or a system error — and refreshes the update screen accordingly.

Lines 358–394

CLEAR-CURRENT-SCREEN

Resets the user update screen to a blank state, discarding any data currently displayed without saving changes. This allows the administrator to start fresh when editing a user account, clearing all previously entered or retrieved field values from the screen.

Lines 395–402

INITIALIZE-ALL-FIELDS

Resets the user update screen to a blank state, clearing all previously displayed user profile data and any status messages. This prepares a clean slate for the administrator to enter a new User ID lookup or begin a fresh update session.
