CSUTLDTC.CBL

Validate whether a given date string is a legitimate calendar date according to a specified date format, returning a validation result to the calling program.

This program acts as a reusable date validation utility within the CardDemo credit card management system. It accepts a date value and its expected format mask from a calling program, then invokes the IBM Language Environment CEEDAYS API to attempt conversion of the date into a Lillian day number (an internal numeric representation of a calendar date). If the conversion succeeds, the date is confirmed as valid; if it fails, the specific reason for invalidity (e.g., bad value, invalid month, non-numeric data, unsupported range) is identified and returned to the caller. The validation result, along with severity and message codes, is passed back so the calling program can take appropriate business action such as rejecting a transaction, flagging an account record, or prompting a user to correct an entry.

Business Rules
  • A date is only considered valid if the CEEDAYS API successfully converts it to a Lillian day number with a zero feedback condition (FC-INVALID-DATE condition name, which paradoxically signals success).
  • The date format mask must be explicitly provided by the caller, meaning the system enforces strict format-aware validation rather than accepting ambiguous date strings.
  • Nine distinct categories of date invalidity are recognised and individually reported, enabling calling programs to provide precise error feedback to users or downstream processes.
  • The validation result severity is propagated back as the program RETURN-CODE, allowing calling programs and job control to detect and react to date validation failures programmatically.
  • The program is a shared utility (called via CALL), meaning all date validation across the CardDemo system is centralised here, ensuring consistent date integrity rules are applied to transactions, accounts, and card records system-wide.
  • Dates must be numeric where required by the format mask; alphanumeric or corrupted date fields are explicitly rejected with a 'Non-numeric data' result.
  • Dates must fall within the supported range of the IBM CEEDAYS API; historically extreme or future dates beyond system limits are rejected as unsupported.
