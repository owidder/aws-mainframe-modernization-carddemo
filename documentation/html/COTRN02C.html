COTRN02C.CBL

Allow authorised users to manually add a new credit card transaction record to the CardDemo transaction ledger.

The program presents a data-entry screen where a bank operator can record a new credit card transaction by supplying either an Account ID or a Card Number (the system cross-references the other automatically), together with full transaction details such as type, category, source, amount, description, origination date, processing date, and merchant information. All entered fields are validated for completeness, correct format, and referential integrity (account/card must exist in the cross-reference file) before the transaction is written. The operator must explicitly confirm the addition (Y/N prompt) before the record is committed to the TRANSACT file, providing a deliberate two-step authorisation safeguard against accidental data entry.

Business Rules
  • Either an Account ID or a Card Number must be provided; the system will automatically resolve and populate the other via the cross-reference file — both cannot be blank.
  • Account ID must be numeric and must exist in the card-to-account cross-reference (CXACAIX); an invalid or non-existent account is rejected.
  • Card Number must be numeric and must exist in the card-to-account cross-reference (CCXREF); an invalid or non-existent card number is rejected.
  • All transaction fields are mandatory: Transaction Type Code, Category Code, Source, Description, Amount, Origination Date, Processing Date, Merchant ID, Merchant Name, Merchant City, and Merchant Zip.
  • Transaction Type Code and Category Code must be numeric values.
  • Transaction dates (Origination Date and Processing Date) must be valid calendar dates, verified by calling the CSUTLDTC date-validation utility.
  • The operator must explicitly confirm the transaction addition by entering 'Y' in the confirmation field; entering 'N' or leaving it blank re-displays the screen with a prompt to confirm, preventing accidental writes.
  • If the session is entered without a prior communication area (EIBCALEN = 0), the user is redirected to the sign-on screen (COSGN00C), enforcing authenticated access.
  • PF3 returns the operator to the calling program (or the main menu COMEN01C if no calling program is recorded), PF4 clears the current screen, and PF5 copies the last transaction's data onto the form to assist with repetitive data entry.
