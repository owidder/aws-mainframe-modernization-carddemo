COPAUS1C.CBL

Detail view of a pending credit card authorization message with the option to mark transactions as fraudulent or remove the mark.

The program displays the complete details of a single pending authorization request to a bank employee – including card number, amount, date/time, merchant information, authorization status (approved/declined), and reason for decline. The employee can page forward through authorization records (PF8) or return to the overview screen (PF3). A key business function is fraud reporting: using PF5, the employee can flag a transaction as fraudulent or remove an existing fraud flag – the action is processed via the program COPAUS2C and persisted in the IMS database. In case of an error, the database change is rolled back.

Business Rules
  • A transaction is considered approved if the authorization code is '00'; all other codes result in it being displayed as declined (highlighted in red).
  • Decline reasons are looked up from a hard-coded table with 10 entries; unknown codes are displayed as 'ERROR'.
  • A fraud flag is a toggle: if a transaction is already flagged as fraud (PA-FRAUD-CONFIRMED), the flag is removed; otherwise, it is reported as fraud.
  • Fraud actions are processed via the external program COPAUS2C; in case of an error (EIBRESP ≠ NORMAL or WS-FRD-UPDT-FAILED), the database change is fully rolled back (ROLLBACK).
  • The program can only be invoked if a valid account number (numeric) and a selected authorization key from the overview screen (COPAUS0C) are present.
  • Using PF8, the operator can navigate to the next pending authorization for the same account; at the end of the list, an appropriate informational message is displayed.
  • Using PF3, the operator returns to the authorization overview (COPAUS0C) without making any changes.
  • IMS database accesses are finalized with a Syncpoint upon completion to ensure data consistency.

This paragraph controls the fraud reporting of a pending authorization transaction: it automatically detects whether a fraud flag should be set or removed (toggle logic), delegates the database update to the fraud program COPAUS2C, and ensures data consistency through rollback in the event of errors.

This paragraph controls the return to the authorization overview (COPAUS0C) when the employee presses PF3. The current program identity is written to the communication area before control is transferred to the overview program.

SEND-AUTHVIEW-SCREEN

Prepares the detail view of a pending authorization message for screen output and displays it to the bank employee – either as a full new display (screen clear) or as an updated view.

Lines 373–397

RECEIVE-AUTHVIEW-SCREEN

Receives the bank employee's input from the detail view of the authorization message – in particular the key commands (e.g., PF5 for fraud reporting, PF8 for scrolling forward, PF3 for return) as well as any screen fields.

Lines 398–408

POPULATE-HEADER-INFO

Populates the header area of the detail view with application titles, transaction and program identifiers, and the current system date and time, so that the bank employee can trace the processing context and the time of the display.

Lines 409–430

READ-AUTH-RECORD

Loads the complete details of a single pending authorization request from the IMS database – first the account summary record, then the specific detail record of the selected transaction.

Lines 431–492

READ-NEXT-AUTH-RECORD

Retrieves the next pending authorization record for the same account from the IMS database, in order to display the next authorization request to the employee when scrolling forward (PF8).

Lines 493–519

UPDATE-AUTH-DETAILS

Writes the updated authorization (with the fraud flag set or removed) permanently to the IMS database and confirms the result to the employee – or rolls back all changes completely in the event of a database error.

Lines 520–556

TAKE-SYNCPOINT

Commits all database changes made (e.g., setting or removing a fraud flag) definitively, thereby ensuring the permanent consistency of the authorization data in the IMS database.

Lines 557–564

ROLL-BACK

Reverses all database changes of the current transaction to maintain data consistency – called when fraud reporting or removal has failed and no inconsistent state may remain in the IMS database.

Lines 565–573

SCHEDULE-PSB

Establishes the connection to the IMS authorization database by allocating the required database access plan (PSB) – a prerequisite for reading authorization details and writing fraud flags.
