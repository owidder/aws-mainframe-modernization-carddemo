CORPT00C.CBL

Allows bank operations staff to request and submit transaction reports (monthly, yearly, or custom date range) for the credit card portfolio by launching a batch reporting job directly from an online CICS screen.

The program presents an online screen where an authorised user selects a report period type: Monthly (automatically covering the current calendar month), Yearly (automatically covering the full current calendar year), or Custom (where the user manually enters a start and end date). After validating the selected dates, the program constructs a complete JCL job stream — including the date range parameters — and submits it to the internal reader (an extra-partition Transient Data Queue), which causes the mainframe job scheduler to execute the batch transaction report program (TRANREPT procedure) asynchronously. The resulting report covers credit card transactions stored in the TRANSACT file for the specified period.

Business Rules
  • Monthly report: date range is automatically set to the first day through the last day of the current calendar month — the user does not manually enter dates.
  • Yearly report: date range is automatically set to January 1st through December 31st of the current calendar year — the user does not manually enter dates.
  • Custom report: all six date fields (start month, start day, start year, end month, end day, end year) are mandatory — any missing field produces a specific field-level error message and halts submission.
  • Custom date fields must be numeric and within valid calendar ranges: month must be 01–12, day must be 01–31.
  • Date validation is performed using the CSUTLDTC utility (which calls CEEDAYS) to confirm that entered dates are real calendar dates before job submission.
  • The batch job is submitted via an extra-partition Transient Data Queue (internal reader), meaning the report runs asynchronously and does not block the online user session.
  • Navigation: PF3 returns the user to the main menu (COMEN01C); if the session is new (EIBCALEN=0), the user is redirected to the sign-on screen (COSGN00C).
  • Only one report type (Monthly, Yearly, or Custom) may be selected per submission; the program evaluates them in priority order.

MAIN-PARA

MAIN-PARA is the central control paragraph that governs the entire lifecycle of the report request screen session: it determines whether the user is new or returning, routes them to the correct screen or action based on their input, and ensures the session remains active after each interaction.

Lines 163–207

PROCESS-ENTER-KEY

This paragraph handles the user's report submission request by determining the selected report type (Monthly, Yearly, or Custom), calculating or validating the appropriate date range, and triggering the batch transaction report job. It enforces all business rules around date completeness, numeric validity, and calendar correctness before allowing the job to be submitted.

Lines 208–461

SUBMIT-JOB-TO-INTRDR

This paragraph handles the final confirmation step before submitting the batch transaction report job to the mainframe scheduler. It validates the operator's explicit yes/no confirmation, then sequentially writes each line of the pre-built JCL job stream to the internal reader queue, which triggers asynchronous execution of the batch report.

Lines 462–514

WIRTE-JOBSUB-TDQ

This paragraph physically submits one line of the constructed batch job to the mainframe internal reader queue, which triggers asynchronous execution of the transaction report. If the submission fails, it raises an error and returns the user to the report request screen with an appropriate message.

Lines 515–539

RETURN-TO-PREV-SCREEN

Transfers control back to the previous screen in the CardDemo application, ensuring the user is returned to an appropriate destination — defaulting to the sign-on screen if no prior navigation context exists. This supports the PF3 back-navigation business rule, maintaining a coherent user session flow.

Lines 540–555

SEND-TRNRPT-SCREEN

Renders the transaction report request screen to the bank operations user, displaying any validation messages or status information. It determines whether to fully refresh the screen or perform a lighter update, then hands control back to CICS to await the next user interaction.

Suspends the current online session and returns control to CICS, keeping the report request screen active and ready to receive the next user interaction. The session context and any in-progress data are preserved so the screen can be redisplayed seamlessly when the user next interacts with it.

Captures the report request submitted by the bank operations staff member from the online transaction report screen, reading all field entries (report type selection and any custom date inputs) into memory for subsequent validation and processing.

Populates the standard screen header area with current date, time, application titles, transaction identity, and program identity before displaying the report request screen to the user. This ensures every screen presented to bank operations staff carries consistent, accurate contextual information for audit and navigation purposes.

Resets the report request screen to a clean state before presenting it to the user, clearing all previously entered or displayed values so that no stale data from a prior session or submission influences the new request.
