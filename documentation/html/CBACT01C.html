CBACT01C.CBL

Batch program that reads all credit card account records sequentially and distributes account data into multiple output files in different formats for downstream processing and reporting.

The program performs a full sequential read of the master credit card account file and, for each account, writes the account data to three different output files: a flat sequential file containing full account details, an array-structured file containing multi-occurrence balance and debit data, and a variable-length record file containing two record types (a short status record and a longer financial summary record). During processing, the card reissue date is reformatted via a date conversion utility (COBDATFT) before being written to the output file. The program logs all account fields to the system console for audit/tracing purposes and abends with an error if any file operation fails.

Business Rules
  • Every account in the master account file is processed — this is a full-file extract with no filtering by account status or balance.
  • If the current cycle debit amount for an account is zero, a default value of 2525.00 is substituted in the flat output file, suggesting a minimum or placeholder debit figure is required by downstream systems.
  • The card reissue date must be reformatted using the COBDATFT date conversion utility (type 2 input, type 2 output) before being written to the output file, ensuring a consistent date format for downstream consumers.
  • The array output file always populates exactly three balance/debit occurrences per account: occurrences 1 and 2 use the actual current balance with hardcoded debit values (1005.00 and 1525.00), while occurrence 3 uses hardcoded negative values (-1025.00 balance, -2500.00 debit), suggesting test data generation or scenario modelling rather than live production data.
  • Two variable-length records are written per account to the VBRCFILE: a 12-byte short record (ID + status) and a 39-byte longer record (ID + balance + credit limit + reissue year), supporting downstream systems with different data granularity needs.
  • Any file I/O error (open, read, or write) on any of the four files causes an immediate program abend, ensuring no partial or corrupt output is silently produced.
  • All account field values are written to the system console log for each record processed, providing a full audit trail of the batch run.
