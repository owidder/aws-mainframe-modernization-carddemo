COACCT01.CBL

Retrieve and return credit card account details in response to incoming service requests received via IBM MQ messaging queues.

COACCT01 operates as a CICS-hosted MQ message listener that receives account enquiry requests from an input queue, looks up the corresponding credit card account record from the ACCTDAT file using an account ID key, and returns the account details to a reply queue (CARD.DEMO.REPLY.ACCT). The program processes messages in a loop until no more requests are pending, handling errors by routing failed messages to a dedicated error queue (CARD.DEMO.ERROR). Each response includes key account attributes such as account status, current balance, credit limit, cash limit, open date, expiry date, reissue date, current cycle credits and debits, and group ID.

Business Rules
  • Account enquiry requests must be received via MQ and must contain a valid function code and numeric account ID key to be processed.
  • If the CICS RETRIEVE of the MQ trigger message fails, the program routes an error and terminates — no account lookups are attempted without a valid input queue name.
  • All account responses are sent exclusively to the fixed reply queue CARD.DEMO.REPLY.ACCT, ensuring responses are routed to the correct downstream consumer.
  • Any processing errors (MQ open failures, retrieval errors) are written to the dedicated CARD.DEMO.ERROR queue to support operational monitoring and recovery.
  • The program continues processing requests in a loop until the input queue is exhausted (no more messages), ensuring all pending enquiries in a batch of requests are fulfilled before termination.
  • Account data returned includes financial limits (credit and cash), current balance, billing cycle activity, and lifecycle dates, supporting downstream account display or decisioning processes.

1000-CONTROL

This paragraph orchestrates the end-to-end control flow for processing credit card account enquiry requests: it initialises the messaging environment, establishes the input queue identity from the MQ trigger, opens all required queues, and drives the account enquiry processing loop until all pending requests are fulfilled.

2400-OPEN-OUTPUT-QUEUE

Establishes the connection to the MQ reply queue (CARD.DEMO.REPLY.ACCT) so that account enquiry responses can be delivered to the requesting application. If the queue cannot be opened, the failure is logged and the program terminates gracefully to prevent undeliverable responses.

Lines 255–288

2100-OPEN-ERROR-QUEUE

Establishes a connection to the dedicated error queue (CARD.DEMO.ERROR) so that any failed or unprocessable account enquiry messages can be routed there for operational investigation and recovery. If the error queue itself cannot be opened, the program logs the failure and terminates immediately, as there is no safe way to handle errors without this fallback channel.

3000-GET-REQUEST

Attempts to retrieve the next pending account enquiry request from the input MQ queue, and either hands it off for processing, signals that all requests have been fulfilled, or escalates an error if the queue cannot be read.

4000-PROCESS-REQUEST-REPLY

Processes an incoming credit card account enquiry request by validating the request, retrieving the account master record, and returning the account details — or an appropriate error message — to the reply queue.

Publishes the assembled account enquiry response to the designated reply queue (CARD.DEMO.REPLY.ACCT), making the account details available to the requesting downstream application. Lines 462–500

9000-ERROR

Routes a failed account enquiry processing error to the dedicated MQ error queue (CARD.DEMO.ERROR), ensuring operational teams can identify, investigate, and recover unprocessable messages. If the error queue itself cannot accept the message, the program performs a controlled termination to prevent silent data loss.

Lines 501–537

8000-TERMINATION

Performs an orderly shutdown of all MQ messaging channels used during the account enquiry session, ensuring that the input, reply, and error queues are properly released before the program exits. This prevents resource leaks and ensures the MQ infrastructure remains available for subsequent service requests.

Lines 538–551

5000-CLOSE-INPUT-QUEUE

Formally releases the bank's connection to the account enquiry input queue once all pending requests have been processed, ensuring the messaging channel is cleanly closed and any closure failure is logged and escalated before the program terminates.

Lines 552–573

5100-CLOSE-OUTPUT-QUEUE

Closes the reply queue (CARD.DEMO.REPLY.ACCT) once all account enquiry responses have been dispatched, releasing the messaging channel cleanly. If the closure fails, the program records the failure details and triggers a controlled termination to prevent resource leaks or incomplete processing.

Lines 574–596

5200-CLOSE-ERROR-QUEUE

Releases the bank's dedicated error queue (CARD.DEMO.ERROR) once all failed messages have been handled, ensuring the messaging channel is properly shut down. If the queue cannot be closed cleanly, the program logs the failure and initiates a controlled termination to protect operational integrity.
